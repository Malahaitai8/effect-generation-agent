# 两次特效链路试跑方法沉淀

## 1. 文档目的

本文记录两次热点视频试跑实际采用的方法，便于后续编写“特效生产 Agent”具体 Skill 时参考。

两次试跑的核心目标不是验证最终生成质量，而是验证以下过程能否成立：

`热点视频 → 客观理解 → 卖点判断 → 链路类型选择 → 节点与模型设计 → 素材处理 → Prompt → 静态校验与交付`

需要区分两类能力：

- **试跑中实际使用的能力**：视频抽帧、视觉理解、文本分析、链路规划、Prompt 编写和文档输出。
- **方案中规划但未实际调用的模型**：生图模型、生视频模型和 RAG。这些只完成了选择与参数设计，尚未验证真实效果。

### 1.1 根据两次试跑，原 Skill 需要做的优化

原来的七步主干可以保留，不需要推翻。需要优化的是步骤之间的数据传递、部分判断规则以及验证边界。

| 优化项 | 当前问题 | 建议调整 |
|---|---|---|
| 任务级结构化结果 | 每一步输出长文本并重复传递，容易增加 Token，也不利于局部修改和断点重跑 | 每个任务维护一个 `task-state.json`；各步骤只写入自己的字段，后续按字段读取。 |
| 视频预处理能力 | 视频抽帧、元数据读取和录屏噪声识别目前依赖临时操作 | 增加固定预处理脚本，统一输出元数据、时间戳关键帧、接触表和录屏噪声标记。 |
| Step 1 与 Step 2 的职责边界 | 视频事实和业务判断容易混在一起，误判后难以定位 | Step 1 只输出事实叙事、时间线和结构化观察；Step 2 再判断卖点和复刻诉求。 |
| Step 3 链路选择规则 | 第一例只关注人物/服装状态，忽略近景、全景、空间位置和构图变化，导致误判为单图驱动 | 把关键景别、构图和空间位置纳入“关键视觉状态”；把连续动作、物理互动、节奏和叙事顺序作为参考视频驱动的重要依据。 |
| 卖点输出约束 | 强制四选一或强制次卖点，可能为了符合格式而制造不必要结论 | 分类仅作为标签；主卖点保留自然语言描述和证据；次卖点允许为空。 |
| RAG 调用方式 | 多个步骤重复召回会增加 Token，也可能让不同步骤使用互相不一致的案例 | Step 3 只做一次主召回并保存任务级案例快照；Step 4、Step 6 按需读取。补充召回先只保留能力入口。 |
| Step 3 与 Step 4 解耦 | 链路类型和具体模型节点容易混在一起 | Step 3 只选择单图、多图或参考视频驱动；Step 4 再设计节点、模型、输入输出和素材。 |
| 链路模板 | `chain-selection.md` 如果同时负责召回和节点设计，后续难以单独复用 | 将案例召回、链路选择、通用节点设计和三类链路模板拆开。 |
| 素材选择规则 | 容易默认使用封面或随意选“好看”的关键帧 | 根据节点控制目标选择素材：静态关键状态用关键帧，连续过程用完整参考视频；封面只有满足节点需求时才使用。 |
| 模型能力与状态 | 方案中写出模型名称后，容易被误解为已经确认接口或生成质量 | 维护 `model-capabilities.json`，并标记 `planned`、`capability_checked`、`executed`、`quality_verified`。 |
| Prompt 生成 | Prompt 与前置观察、卖点和节点之间的来源关系不够明确 | 按节点生成 Prompt，并记录身份、动作、镜头、素材和风险分别来自哪个步骤；保留简短与详细 Prompt 的实测空间。 |
| 静态校验 | 容易与成片质量评估混为一谈 | Step 7 只检查方案完整性、自洽性和可执行性；模型效果必须在真实生成后另行验收。 |
| 失败处理 | 在核心链路尚未验证前就细化补搜、降级和质量修复，会使第一版过重 | 第一版只记录风险和可选补救；实际失败后再增加补搜、后处理、重试或替代模型。 |

两次试跑对链路规则的验证范围需要谨慎表述：

- 第一例暴露并补充了多图驱动中“关键景别、构图和空间位置”的判断维度。
- 第二例独立验证了“连续动作、物理互动和叙事顺序适合参考视频驱动”这条规则。
- 第二例不能证明第一例的多图规则已经得到充分验证；三类链路仍需要更多案例覆盖。

### 1.2 静态校验是什么

静态校验是指：**在不调用生图、生视频模型的情况下，检查七步流程产出的方案是否完整、自洽、可追溯并具备执行条件。**

它检查的是“方案有没有明显问题”，不是“生成出来的视频好不好”。

#### 静态校验检查项

| 检查项 | 具体检查内容 | 能发现的问题 |
|---|---|---|
| 步骤完整性 | Step 1–6 是否都有输出，必填字段是否缺失 | 没有卖点结论、没有素材清单、没有 Prompt 等流程断档。 |
| 职责边界 | Step 1 是否混入卖点或模型判断，Step 3 是否提前设计具体节点 | 上游结论污染下游判断，导致错误难以定位。 |
| 事实可追溯性 | 卖点、控制要求和链路理由能否对应到视频观察中的事实 | 凭空判断“为什么火”，或选择了视频中不存在的动作。 |
| 链路类型合理性 | 关键状态数量、构图变化、连续动作和时序要求是否支持所选类型 | 本应多图却选单图、本应参考视频却只用首帧。 |
| 节点连通性 | 上一节点输出能否作为下一节点输入；是否存在没有来源或无人使用的素材 | Node 2 需要一张图，但前面没有节点生成；生成了素材却没有节点使用。 |
| 最小必要性 | 每个节点是否直接服务于卖点或必要控制要求 | 在第一轮加入没有必要的生图、补搜或后处理节点。 |
| 素材覆盖 | 每个节点需要的用户图、关键帧、完整视频或其他素材是否齐全 | 链路写得出来，但缺少真正可提交给模型的输入。 |
| 模型能力匹配 | 候选模型的输入类型和能力是否与节点要求相符，验证状态是否如实标注 | 给只支持单图的模型传多图，或把未调用模型写成已验证。 |
| Prompt 对齐 | Prompt 是否覆盖节点目标、主体身份、关键动作、镜头、状态和风险 | 链路要求换人，Prompt 却没有说明替换对象；要求连续时序但 Prompt 顺序含糊。 |
| 风险与边界 | 不确定项、模型风险和可能的后续补救是否被记录 | 方案看似确定，实际存在文字生成、身份一致性等未说明风险。 |
| 最终交付一致性 | 最终输出是否与前面的链路、节点、模型和 Prompt 一致 | 分析选择参考视频驱动，最终结果却写成多图驱动。 |

#### 静态校验有什么用

1. **在调用昂贵模型前拦截低级错误。** 避免因为节点断裂、素材缺失或模型输入不匹配而浪费生成次数。
2. **判断方案是否具备进入真实生成的条件。** 校验通过表示可以开始实测，不表示视觉效果已经通过。
3. **定位问题属于哪一步。** 可以区分是视频观察错、业务判断错、链路类型错，还是节点和 Prompt 没有对齐。
4. **支持人工修改和断点重跑。** 修改某个字段后，可以只重跑受影响的后续步骤。
5. **为后续工作流自动化提供门槛。** 只有静态校验通过，才允许提交生图或生视频任务。

#### 静态校验不能替代什么

静态校验不能判断以下内容：

- 人物身份在成片中是否稳定；
- 动作、镜头和物理交互是否自然；
- 文字是否拼写正确；
- 图片或视频是否足够美观；
- 某个 Prompt 实际效果是否优于另一个 Prompt；
- 候选模型的真实成功率和稳定性。

这些必须在真实模型生成后进行结果验收。更准确的流程是：

`静态校验通过 → 执行生成 → 检查报错与结果质量 → 记录实测结论`

第一阶段如果暂不建设自动质量评估，生成后可以先由人工查看结果；静态校验仍然有价值，因为它负责保证送入模型之前的方案是完整且可执行的。

## 2. 两次测试对象

| 测试 | 热点效果 | 独立分析得到的链路 | 对照设计师后的结果 |
|---|---|---|---|
| 测试一 | 古风人物转身，镜头从近景拉远至桥上全景，出现心形花瓣并散开 | 初判单图驱动，三节点 | 设计师使用两张关键构图图，说明应归为多图驱动；暴露出链路选择规则对“景别/构图变化”考虑不足。 |
| 测试二 | 车窗下降露出人物吹蜡烛，随后升起，文字从 Happy 过渡到 Birthday | 参考视频驱动，最短单视频节点 | 与设计师的“人物图＋完整参考视频＋换人指令”一致，说明链路类型判断有效。 |

## 3. 试跑中实际使用的方法

### 3.1 视频预处理

使用本地视频处理工具读取视频基础信息并按固定频率抽帧：

- 获取时长、分辨率和帧率。
- 以约每秒 2 帧的频率生成时间线抽帧。
- 生成接触表，用于快速观察完整叙事和状态变化。
- 根据时间线选择起点、关键转折点和终点帧。
- 对录屏视频识别黑边、鼠标、播放器界面和水印等噪声。

本环节实际使用的是 **FFmpeg 类视频处理能力**，不是生成模型。

后续 Skill 可由 `scripts/extract-video.py` 或同类脚本承接。当前目录结构中尚未包含该脚本，建议补充，因为两次测试都依赖视频抽帧和元数据读取。

建议输出：

```json
{
  "video_metadata": {},
  "timeline_frames": [],
  "contact_sheet": "",
  "screen_recording_artifacts": []
}
```

### 3.2 Step 1：视频客观理解

实际方法：将时间线总览与关键帧交给具备视觉理解能力的多模态模型分析，再由文本模型整理为事实叙事、时间线和结构化特征。

使用能力：

- VLM：识别主体、场景、动作、表情、运镜、视觉元素、文字和状态变化。
- LLM：把逐帧观察整理为连续故事与时间线。

对应 Skill 文件：`prompts/vlm-observation.md`。

建议输入：

- 视频元数据；
- 接触表；
- 关键帧及其时间戳；
- 原视频，可选，用于关键动作难以从抽帧判断的情况。

建议输出：

```json
{
  "factual_narrative": "",
  "timeline": [],
  "subjects": [],
  "scene": {},
  "actions": [],
  "expressions": [],
  "camera": [],
  "visual_elements": [],
  "state_changes": [],
  "observed_text": [],
  "uncertainties": []
}
```

关键约束：只回答“看到了什么”，不得提前判断卖点、链路和模型。

### 3.3 Step 2：业务判断

实际方法：仅根据 Step 1 的观察结果，判断热点最有辨识度的部分和用户真正需要复刻的内容。

使用能力：LLM 文本推理，不需要再次调用 VLM。

对应 Skill 文件：`prompts/selling-point.md`。

两次测试采用的判断维度：

- 主卖点是什么，删除它后视频是否仍成立；
- 是否存在有必要记录的次卖点；
- 用户要替换什么、必须保留什么；
- 判断依据对应 Step 1 中的哪些事实；
- 当前有哪些不确定项需要实测。

卖点不应被强制限定为固定四类中的唯一标签，也不强制必须存在次卖点。分类标签可用于检索和统计，但最终应允许自然语言描述。

### 3.4 Step 3：执行链路类型选择

实际方法：先把“必须保留的内容”和“需要控制几个关键视觉状态”融合分析，再选择单图驱动、多图驱动或参考视频驱动。

使用能力：LLM 规则判断。本轮两次测试均未调用 RAG。

对应 Skill 文件建议拆为：

- `prompts/case-retrieval.md`：构造一次 RAG 主召回查询并保存任务级案例快照；
- `prompts/chain-selection.md`：结合控制要求和案例快照选择链路类型。

建议判断问题：

1. 是否只需控制一个关键视觉状态，其余动作可由文字描述？
2. 是否有两个或多个必须精准控制的状态、景别或构图？
3. 是否必须复刻连续动作、节奏、表演、镜头或叙事顺序？
4. 原视频是否是比若干静态帧更完整、更可靠的控制信号？

两次测试带来的规则修正：

- 测试一表明，“近景人物”和“桥上全景人物”即使角色外观相同，也属于两个关键视觉状态。链路选择不能只看服装或人物状态，还必须看景别、空间位置和构图变化。
- 测试二表明，车窗升降、吹蜡烛、火焰熄灭和文字变化构成连续时序，适合参考视频驱动，不能仅因存在明确首尾状态就选择多图驱动。

建议输出：

```json
{
  "control_requirements": [],
  "chain_type": "single_image | multi_image | reference_video",
  "reason": "",
  "rejected_types": [],
  "case_snapshot_ref": null,
  "risks": []
}
```

### 3.5 Step 4：具体链路、模型与素材规划

实际方法：在链路类型确定后，由 LLM 设计具体节点序列，给每个生成节点选择候选模型，并列出输入、输出和素材依赖。

使用能力：LLM 规划；未真实调用模型能力接口。

对应 Skill 文件：

- `prompts/chain-design.md`：设计公共节点和完整依赖；
- `prompts/chain-single-image.md`：单图链路模板；
- `prompts/chain-multi-image.md`：多图链路模板；
- `prompts/chain-reference-video.md`：参考视频链路模板；
- `references/model-capabilities.json`：提供可用模型、输入类型和能力边界。

测试一规划的候选模型：

- 人物古风化：可图 2.1 人像参考；
- 场景或关键构图生成：nano2；
- 首帧生视频：Kling Omni 3.0。

上述模型在试跑中均未实际调用。设计师对照方案使用了两次可图 2.1 人像参考和一次 Kling 3.0 Omni，说明我们的节点方向基本存在可执行基础，但模型分配和链路类型初判需要调整。

测试二规划的候选模型：

- 参考视频生成：Kling 3.0 Omni，或其他支持人物图与视频参考的模型。

该模型在试跑中未实际调用。设计师对照方案使用视频 3.0 Omni，并输入人物图和完整参考视频，支持了我们的链路方向判断。

模型选择必须标注状态：

- `planned`：仅为方案候选；
- `capability_checked`：已根据能力表确认接口支持；
- `executed`：已经真实调用；
- `quality_verified`：结果已经人工或自动验收。

这可以避免把“写进方案”误认为“已经验证”。

### 3.6 Step 5：热点素材提取与标准化

实际方法：根据 Step 4 的节点需求，从抽帧中选择关键状态，并判断关键帧、封面或完整视频中哪一种才是生产素材。

使用能力：VLM/LLM 判断＋本地视频和图像处理脚本。

对应 Skill 文件：`prompts/material-extraction.md`，以及建议新增的视频抽帧脚本。

测试一：

- 需要近景主体状态和桥上全景状态；
- 花瓣成心可作为动态 Prompt 内容，不一定要增加第三张输入图；
- 测试暴露出关键帧选择必须服务于“关键构图状态”，不能只选择视觉上好看的画面。

测试二：

- 完整热点视频是生产主素材；
- Happy、人物揭示、吹蜡烛、Birthday 四张关键帧用于分析和验收；
- 关键帧不应替代完整参考视频。

### 3.7 Step 6：Prompt 写作

实际方法：根据视频观察、卖点、链路节点和素材依赖，为每个生成节点分别编写 Prompt 和必要的负向约束。

使用能力：LLM 文本生成。两次测试均未使用 RAG 案例快照。

对应 Skill 文件：

- 公共规则：可放在 `prompts/chain-design.md`；
- 各链路/节点 Prompt：放在三个 `chain-*.md` 模板中；
- 正式接入 RAG 后，从任务级案例快照中按需读取相似节点 Prompt 和审核经验。

Prompt 的信息来源应可追溯：

- 主体和身份约束来自用户输入与 Step 2；
- 场景、动作、镜头和时序来自 Step 1；
- 输入素材及模型能力来自 Step 4；
- 特殊风险来自 Step 3 和 Step 5；
- 案例经验来自 Step 3 保存的任务级 RAG 快照。

测试二与设计师答案出现了“详细 Prompt”和“极简换人 Prompt”的差异。当前只应记录为待验证策略，不应直接用设计师版本覆盖独立分析结果。后续可用同一人物图做 A/B 测试。

### 3.8 Step 7：验证与交付

实际方法：执行静态完整性检查，判断方案是否具备进入真实模型验证的条件，然后输出完整过程文档和最终结果。

使用能力：LLM 规则校验＋人工可读文档生成。

建议将 Step 7 作为 `SKILL.md` 中的统一交付逻辑，不必额外拆成大型 Prompt 文件。它至少检查：

- Step 1–6 输出是否齐全；
- 每个判断能否追溯到前置事实；
- 节点输入输出是否连通；
- 素材是否覆盖全部节点；
- 候选模型是否标明验证状态；
- Prompt 是否与节点目标一致；
- 风险和未验证项是否明确；
- 文档末尾是否存在独立的“最终输出结果”。

## 4. 两次试跑实际使用的模型与工具

### 4.2 两次试跑是否使用了现成 Skill

**没有。** 两次试跑是在 Codex 会话中人工模拟七步流程，没有加载或执行已经封装好的“特效生产 Skill”。

实际组合为：

`FFmpeg 视频预处理 + Codex/GPT-5 多模态观察 + Codex/GPT-5 文本推理与规划 + Markdown 文档输出`

### 5.4 `prompts/chain-selection.md`

```text
你是执行链路类型选择模块。请选择单图驱动、多图驱动或参考视频驱动；本步骤只确定类型，不设计具体节点。

输入：
- 客观观察：{{observation}}
- 业务判断：{{business_judgement}}
- 案例快照摘要：{{case_snapshot_summary}}

1. 是否只需精准控制一个关键视觉状态，其余动作可由文字描述？

  "reason": "",
  "rejected_types": [{"type": "", "reason": ""}],

  "risks": []
}
```

一次任务只维护一个任务级状态对象，各步骤写入自己的结果，后续步骤读取引用，不重复把全部内容输出再输入。

RAG 结果应在 Step 3 保存为任务级案例快照。Step 4 和 Step 6 只按需读取其中相关内容，不要求每一步重新输出和输入完整召回结果。补充召回仅保留为覆盖不足时的扩展能力，当前核心版本不必细化。

## 8. 两次测试对 Skill 规则的直接贡献

### 已验证可保留

- Step 1“客观观察”与 Step 2“业务判断”必须拆开。
- 客观观察必须包含事实叙事和时间线，不能只输出标签。
- Step 3 只确定链路类型，Step 4 再确定具体节点、模型和素材。
- 不接 RAG 时，七步流程仍能生成完整方案。
- RAG 主召回只需在 Step 3 执行一次并保存快照。
- Step 5 应根据具体节点决定使用关键帧、封面还是完整视频。
- Step 7 必须同时记录已完成项、风险和未验证项。

### 需要修正规则

- 多图驱动的判定必须包含多个关键景别、空间位置和构图状态，不能只看角色外观或服装是否变化。
- 参考视频驱动的判定应强调连续动作、物理交互、节奏和叙事顺序，而不是简单统计关键状态数量。
- 主卖点可以分类，但不应被标签替代；次卖点不应强制存在。
- 候选模型必须带验证状态，避免把规划结果误写为已支持或已验证。

### 仍需真实执行验证

- 测试一的修正后多图链路能否稳定完成近景到全景的过渡。
- 测试二中详细 Prompt 与极简换人 Prompt 哪个效果更好。
- 视频模型对人物身份、复杂构图、文字、火焰和物理结构的保持能力。
- RAG 是否能明显改善链路选择、模型分配和 Prompt 质量。
- 静态质量检查之后，是否需要增加自动化成片质量评估。

## 9. 当前结论

两次测试证明，七步框架可以作为 Skill 主骨架，但不能把当前规则视为完全定型：

- 测试一发现了链路类型误判，帮助补齐“关键构图状态”的判断规则。
