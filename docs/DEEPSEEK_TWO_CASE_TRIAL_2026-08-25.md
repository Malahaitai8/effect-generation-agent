# DeepSeek 双类型真实调用试跑记录（2026-08-25）

## 1. 测试目标与方式

本轮从两种目标链路中各选一个已有人工结论的案例：

| 中性任务 ID | 视频 | 人工链路 | Agent 判定 | 是否一致 |
|---|---|---|---|---|
| `deepseek-blind-a` | 浪漫时刻 | 单图驱动 | 单图驱动 | 是 |
| `deepseek-blind-b` | 寿司店老板 | 设计师采用参考视频驱动 | 单图驱动 | 可接受的替代方案，待生成验证 |

两个任务通过 Agent 自身的批次调度运行，批次 ID 为 `deepseek-two-case-20260825`，最大并发数为 2。这里的并发来自项目内的 BatchRunner，不是 Codex 多 Agent。

本轮模型分工：

- Step 1：两个视频均重新执行一次抽帧；为节省重复人工观察时间，复用此前对同一原视频已经完成的 VLM 客观理解与关键帧筛选结果。
- Step 2、Step 3B、Step 4、Step 6：由 Agent 从 `.env.local` 读取配置并真实调用 DeepSeek。
- Step 3A：使用本地 BGE Embedding 召回。
- Step 5、Step 7：由确定性执行器完成。

源视频文件名、任务 ID 和输出目录均不含 `single`、`reference`、`单图驱动` 或 `参考视频` 等答案标签。人工链路只在 Step 3 保存后用于结果核验。

本轮不调用真实生图和视频生成模型，因此验证的是“分析与链路方案是否形成”，不是最终生成视频质量。

## 2. 单图案例：浪漫时刻

### Step 1：客观理解与关键帧

- 一次抽取 10 张候选帧；[时间线抽帧总览](../outputs/deepseek-blind-a/video-analysis/timeline-overview.jpg)。
- `frame_0001`：人物、餐桌、夜景和右上方悬挂蛋糕的起始空间关系，保留下游。
- `frame_0004`：蛋糕下降、人物抬手和完整花束丝带的中间状态，保留下游。
- `frame_0006`：蛋糕已被托住、花束尚未消散且遮挡面部的转折状态，仅作时序证据。
- `frame_0009`：人物正面微笑、居中托住蛋糕、花瓣飘落的结束状态，保留下游。
- 视频被理解为固定机位的小叙事：蛋糕下降，人物托接，心形花束散成花瓣，人物最终托住蛋糕微笑。

### Step 2：卖点与复刻目标

- 主卖点：蛋糕从右上悬空下降并被人物双手托接，同时心形玫瑰花束散成粉色花瓣，形成完整的惊喜递送和祝福氛围。
- 需要保留：下降与托接关系、花束消散、表情变化、固定机位、半身构图、浅景深和花瓣效果。
- 可以适配：人物身份和外观、蛋糕及花束细节、桌面装饰和背景。
- 无必要 Prompt 分支。

首次运行时，DeepSeek 把 `uncertainties` 写成对象数组，并把 `alternative_interpretations` 写成不完整对象，未通过 Schema；自动修正一次后仍失败。修订通用 Step 2 Prompt，明确两者的准确类型后，同一任务通过恢复机制重新执行并成功，不需要人工代写业务结果。

### Step 3：案例召回与链路选择

- 选择：`single_image`，与人工结论一致。
- 判断理由：首帧可以建立人物、蛋糕、花束、场景和构图；蛋糕下降、托接和花瓣飘落被判断为可用时序 Prompt 表达的短时线性过程。
- 使用案例：`duck_hairdressing`、`time_space_magpie_bridge`、`qixi_sky_lantern`。
- 风险：案例库没有完全同构的蛋糕托接案例；蛋糕和双手的接触轨迹仍需真实生成验证。

### Step 4：节点链路设计

1. 运行时用户图输入。
2. 使用“可图 2.1 人像参考”生成浪漫餐桌场景首帧。
3. 使用 Kling 2.5 Turbo，以首帧为唯一图片输入生成 5 秒视频。

该节点结构符合单图驱动的最终入参边界。

### Step 5：固定素材准备

本方案不依赖热点视频片段等固定素材，因此无需加工素材，`ready_for_prompting=true`。未来运行时用户图只是输入槽位，当前不存在不会让任务暂停。

### Step 6：节点 Prompt

- 首帧 Prompt：建立人物、夜景餐桌、悬挂蛋糕、心形花束、丝带和起始视线关系。
- 视频 Prompt：按“抬手—蛋糕下降—双手托接—花束消散—托蛋糕微笑”的顺序描述动作和变化，并要求人物、蛋糕、场景和构图保持一致。

### Step 7：最终交付

节点、素材、Prompt 和案例引用检查均通过，生成设计师可读方案：

- [浪漫时刻最终链路方案](../outputs/deepseek-blind-a/production-plan.md)
- [浪漫时刻完整七步记录](../outputs/deepseek-blind-a/task-result.json)
- [浪漫时刻案例快照](../outputs/deepseek-blind-a/case-snapshot.json)

### 结果分析

链路判断、节点结构和 Prompt 时序基本合理。当前方案能够告诉设计师需要什么运行时输入、先生成什么首帧、再使用什么视频模型以及每个节点的 Prompt。

仍有三个问题：最终风险存在重复内容；模型能力配置仍是案例观察信息，不是已验证接口能力；真实生成时必须验证蛋糕是否穿脸、穿手以及花束消散是否稳定。

## 3. 设计师采用参考视频链路的案例：寿司店老板

### Step 1：客观理解与关键帧

- 一次抽取 5 张候选帧；[时间线抽帧总览](../outputs/deepseek-blind-b/video-analysis/timeline-overview.jpg)。
- `frame_0001`：主体造型、料理场景、完整鱼块和初始握刀关系。
- `frame_0003`：一爪按鱼、一爪持刀、鱼片已经分离的中间状态。
- `frame_0005`：鱼片数量累积、切割仍在继续的结束状态。
- 三张关键帧均保留下游。

### Step 2：卖点与复刻目标

- 主卖点：拟人动物穿料理服，用双爪分工完成连续三文鱼切片，切片在砧板前侧逐渐累积。
- 需要保留：拟人动物、双爪分工、握刀和固定食材、刀鱼接触、切片分离与累积、固定近景构图。
- 可以适配：动物物种和外观、服装细节、刀具和食材外观、背景装饰。
- 无必要 Prompt 分支。

### Step 3：案例召回与链路选择

- Agent 选择：`single_image`。
- 设计师历史方案：`reference_video`。
- 结果：两种方案均有合理依据，不能仅凭历史方案把单图判断记为错误；应通过实际生成质量、成功率和成本比较。
- 使用案例：`animal_gel`、`pet_makeup_vanity`、`goldfish_scooping`。

DeepSeek 将动作概括为“刀反复抬起下压、切片累积”的小幅线性循环，并认为首图加文字可以尝试。该判断具有合理性；与此同时，核心卖点还依赖以下连续接触关系：

1. 一只前爪持续固定鱼肉；
2. 另一只前爪持续握住刀柄；
3. 刀刃反复接触、切入并穿过鱼肉；
4. 鱼片从整体分离并在砧板上累积；
5. 宠物前爪、刀和食材在全过程中都不能穿模或变形。

这些“连续接触拓扑和局部物理结果”会提高单图生成风险，但不等于单图一定无法生成。因此更合理的结论是：单图驱动可作为低成本首选试跑，参考视频驱动作为稳定性候选；在没有真实生成结果前，不硬判单图方案无效。

### Step 4：节点链路设计

下游按照 Step 3 的单图方案设计为：

1. 运行时用户图输入。
2. 使用 `image2` 生成宠物厨师持刀首帧。
3. 使用 Kling 3.0 Omni，以首帧为唯一图片输入生成视频。

如果单图实测无法稳定保持双爪、刀具和鱼片分离关系，可升级为：运行时宠物图与热点参考视频共同输入支持参考视频驱动的视频模型；如果没有必须预建的主体视觉状态，不需要额外增加生图节点。

### Step 5：固定素材准备

单图方案不使用热点视频作为固定素材，因此 Step 5 没有复制参考视频并直接进入 Prompt 阶段。若升级参考视频方案，Step 5 才需要准备该固定素材。

### Step 6：节点 Prompt

DeepSeek 分别生成首帧和单图视频 Prompt，并加入大量“不得出现人手、宠物爪不得变成人手、刀具不得变形”的约束。Prompt 能识别风险，但文字约束本身不能替代参考视频提供的连续动作和接触时序。

### Step 7：最终交付

节点、素材、Prompt 和案例引用均完整，因此 Step 7 正常生成了可试跑的单图方案。结构完整仍不代表真实生成效果已经验证。

- [寿司店老板最终链路方案（单图试跑方案）](../outputs/deepseek-blind-b/production-plan.md)
- [寿司店老板完整七步记录](../outputs/deepseek-blind-b/task-result.json)
- [寿司店老板案例快照](../outputs/deepseek-blind-b/case-snapshot.json)

### 结果分析

这条测试证明 Agent 已能由 DeepSeek 自动形成一个有依据的低成本单图方案。RAG 召回的 `pet_makeup_vanity`、`goldfish_scooping` 支持了该方向，但缺少精细工具操作案例，因此还不足以证明方案稳定。

下轮不应针对寿司案例增加硬规则。更合适的是把持续接触、分离和物理结果累积记录为风险与升级条件：允许单图先试；只有模型能力、历史试跑或生成结果证明单图不稳定时，再选择或升级参考视频链路。

## 4. 设计师最终能看到什么

每条任务最终提供一份节点化链路方案，而不是七步 JSON。方案中包含：

1. 热点视频内容和核心卖点；
2. 选择的链路及理由；
3. 未来特效运行时需要的用户输入；
4. 需要预先准备的固定素材；
5. 按执行顺序排列的模型节点、参数和 Prompt；
6. 风险和需要设计师确认的事项。

本轮两份用户方案都可作为后续真实生成试跑输入；寿司店老板尤其适合用来比较单图方案与设计师参考视频方案的成功率、质量和成本。

## 6. 本轮新增发现

1. Step 2 Prompt 原先没有明确区分 Step 1 的不确定性对象与 Step 2 的字符串数组，已修正为精确字段约束。
2. Step 3 可以提出不同于设计师历史方案的低成本可执行方案；边界案例需要生成验证，不能仅按历史链路判错。
3. RAG 召回会显著影响 DeepSeek 判断；相似主体或相似场景不能代替相似控制难度，召回覆盖不足应显式成为风险。
4. Step 7 当前校验结构完整性，无法发现上游业务判断错误；后续需要通过评测层对照链路真值，而不是让 Step 7 擅自改写 Step 3。
5. 本轮复用的 Step 1 关键帧业务结果仍保留旧任务中的 `file_ref`，虽然媒体内容相同且不影响本轮推理，但正式复用机制应将引用重新绑定到当前任务抽帧目录。

## 7. 中文卖点标签实现

在不破坏历史案例和 RAG 的前提下，卖点标签采用双层表达：

- `task-result.json`、案例库和检索继续保存稳定英文 ID，例如 `physical_interaction`；
- 设计师看到的 `production-plan.md` 通过统一映射显示中文，例如“物理互动”；
- 未进入映射表的新标签原样显示，避免扩展标签被丢弃。

当前初始词表已经全部覆盖，包括身份或角色转换、宠物拟人化、风格转换、场景奇观、特效奇观、状态变化、道具或超能力、动作表演、物理互动、揭示或微叙事、文字或符号揭示、节日或仪式、镜头或构图、音画同步。

该改动只影响用户交付层，不改变 Step 2 输出、案例数据、Embedding 文本和标签 Jaccard 计算。自动化测试已覆盖已知标签翻译和未知标签回退。

### 8.1 达康书记摇车窗：七步结果

#### Step 1：客观理解与关键帧

- 一次抽取 16 张候选帧；[时间线抽帧总览](../outputs/deepseek-blind-c/video-analysis/timeline-overview.jpg)。
- `frame_0001`：两辆车、道路和猫位于开启车窗处的完整起始关系。
- `frame_0008`：猫正面外观和开窗状态最清晰。
- `frame_0010`：猫从正面凝视转为侧向回头。
- `frame_0012`：玻璃升至颈部附近，记录遮挡中态。
- `frame_0016`：玻璃接近关闭，猫隔着反光玻璃仅见轮廓。
- 五张关键帧均保留下游。

#### Step 2：卖点与复刻目标

- 主卖点：车窗从下向上连续升起，主体从完全可见逐步变为隔着反光玻璃仅见轮廓。
- 次卖点：猫由正面凝视转向车内，与车窗关闭形成动作呼应。
- 需要保留：车窗运动、显隐状态、玻璃反射、主体和车窗层次、侧向近距离视角。
- 可以适配：主体外观、车辆外观和道路细节。
- 无必要 Prompt 分支。

#### Step 3：案例召回与链路选择

- 选择：`single_image`，与历史设计师方向一致。
- 理由：车窗上升是单向线性运动，猫转头和镜头靠近也可用短时 Prompt 表达。
- 选中案例：`jet_ski`。
- 风险：召回案例与车窗遮挡的控制问题差异很大，案例覆盖明显不足。

#### Step 4：节点链路设计

DeepSeek 只设计了一个节点：

`user_image → Kling 2.5 Turbo → generated_video`

这里存在节点设计问题。当前产品中的 `user_image` 是未来终端用户提供的普通主体图，只承担身份信息；但视频 Prompt 要求输入图已经包含猫、汽车、开启车窗、道路和正确遮挡层次。普通用户图无法直接满足这些要求。

更合理的结构应为：

`user_image → 生成汽车开窗场景首帧 → 单图视频模型 → generated_video`

所以本例虽然链路类型判断为单图驱动没有问题，但 Step 4 没有把“运行时身份图”和“视频首帧”分清，少了必要的前置生图节点。

#### Step 5：固定素材准备

当前错误节点图不需要固定素材，因此 `ready_for_prompting=true`。该状态只能说明固定素材完整，不能证明运行时用户图已经具备视频首帧所需场景。

#### Step 6：节点 Prompt

视频 Prompt 对车窗上升、猫转头、玻璃反射和显隐过程描述较完整，但它直接要求“保持输入图中的车窗开启状态、车辆和城市路口背景”，进一步证明该节点实际需要的是已生成的场景首帧，而不是普通用户身份图。

#### Step 7：最终交付

结构校验通过并生成方案，但当前校验只能确认输入 ID 存在，尚不能判断该输入的语义用途是否满足节点 Prompt。

- [达康书记摇车窗完整七步记录](../outputs/deepseek-blind-c/task-result.json)

最终方案中的卖点标签已显示为：**状态变化、物理互动、镜头或构图**。

#### 结果分析

链路方向和视频时序 Prompt 有可用基础，但不能直接进入真实生成：必须先在 Step 4 增加首帧生图节点，并让 Step 6 为该节点生成独立 Prompt。该问题应通过通用规则修正：如果视频节点要求的场景、构图、姿态或道具不可能来自普通运行时身份图，就必须由上游节点预先建立目标视觉状态。

### 8.2 功夫小猫：七步结果

> 后续修复（2026-08-25）：Schema 已升级到 `0.6.0`。Step 2 的 `replace/preserve/adapt/optional` 现使用稳定约束 ID；Step 3 每个 `must_preserve` 必须显式引用 Step 2 `preserve` 或 `control_signals`。运行时会阻断将 `replace`、`adapt` 或 `optional` 内容升级为必保留项。本节仍保留当时错误输出，用于说明问题如何被发现。
