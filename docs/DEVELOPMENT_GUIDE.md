# 特效生成 Agent 开发协作与技术基线

> 状态：持续迭代中  
> 当前阶段：人工协作式链路设计 MVP 与 RAG 并行建设  
> 文档职责：本项目唯一的人类可读开发入口

本文件统一维护完整 Agent 的产品目标、宏观架构、当前实现边界、Schema 演进原则、实施路线和协作上下文。它用于帮助新的开发者或 Codex 任务快速理解项目并继续工作，不要求所有设计在当前阶段一次冻结。

机器可执行的约束仍以代码中的对应文件为准：

- 任务字段与校验：`schemas/task-result.schema.json`
- Skill 路由与七步流程：`skills/effect-generation-workflow/SKILL.md`
- Step 具体输入输出：`skills/effect-generation-workflow/prompts/`
- 案例数据与召回实现：`rag/`
- 模型能力配置：`config/model-capabilities.json`
- 当前任务产物：`outputs/<task-id>/`

本文解释这些文件之间的关系和修改原则，不复制完整 Schema、Prompt 或配置内容，避免出现多个事实源。

## 1. 项目目标

### 1.1 完整产品目标

项目最终交付是一个公司内部使用的特效生成 Agent，用于逐步自动化以下流程：

```text
提交热点视频
  → 理解视频内容与时间线
  → 判断卖点和复刻目标
  → 设计特效生成链路
  → 转换为 Keffect 可执行工作流
  → 使用测试素材跑批
  → 验证结果并交付
```

理想使用形态是内部工作台或 API。用户提交一个或一批视频后，Agent 负责调度相关能力、保存中间状态并汇总产物，人工主要处理必要选择、异常情况和最终结果确认。

当前直接用户是特效设计师，本次任务默认只提交热点视频，可选补充固定参考素材。未来使用特效时才提供的人物图、宠物图等只是“运行时输入槽位”，本次不要求文件存在。

内部宏观方案参考：[特效生成 Agent 初步设计文档](https://docs.corp.kuaishou.com/d/home/fcADxCeiORX8PbM3GSwaW-7H-)。

### 1.2 当前 MVP

当前不是一次实现完整终态，而是优先完成“链路分析与方案设计”能力：

- 支持 `single_image`（单图驱动）；
- 支持 `reference_video`（参考视频驱动）；
- 能自动设计并交付案例库覆盖的双图有序状态 `multi_image`（多图驱动）链路；
- 串联既定 Step 1–7；
- 通过案例 RAG 为链路选择、节点设计和 Prompt 提供证据；
- 输出结构化任务结果和人类可读生产方案。

当前主要交付是节点化链路方案，不是已生成的特效视频，也不是 Keffect 工作流。

### 1.3 当前阶段重点

以下工作正在并行推进，无需等待本文完全冻结：

- Step 1–2 的输入输出和 Prompt 细化；
- RAG 的 case、召回和案例快照实现，由并行任务继续收敛；
- Codex 文件交换、确定性素材处理和生产方案交付；
- 本文维护的宏观工程设计、状态维护原则和协作上下文。

真实模型 API、Keffect 转换、结果视频跑批、网站和部署均不属于当前立即交付范围。

## 2. 宏观工程设计

### 2.1 完整 Agent 的模块关系

```text
内部工作台 / API
        │
        ▼
顶层 Agent（任务接收、模块调度、状态与交付）
        │
        ├── 链路设计能力
        │     热点视频 → 结构化链路方案 + Prompt + 方案素材
        │
        ├── Keffect 工作流构建能力
        │     结构化链路方案 → Keffect 可执行工作流
        │
        └── 跑批验证能力
              工作流 + 测试素材 → 结果视频 + 验证记录

横向基础能力：RAG、模型适配、素材管理、任务状态、日志与产物存储
```

### 2.2 顶层 Agent

顶层 Agent 的职责是：

- 接收单个视频或批量任务；
- 调用不同能力模块；
- 管理模块间依赖和任务阶段；
- 处理暂停、恢复、失败与重试；
- 保存并汇总产物；
- 向工作台或 API 返回进度和结果。

顶层 Agent 不直接承担视频卖点判断、链路选择或节点 Prompt 编写。这些领域推理由对应 Skill 或能力模块负责。

### 2.3 三个能力模块

| 模块 | 输入 | 输出 | 当前状态 |
|---|---|---|---|
| 链路设计能力 | 热点视频、用户要求、可用素材 | 结构化链路方案、节点 Prompt、素材引用、`production-plan.md` | 当前重点 |
| Keffect 工作流构建能力 | 结构化链路方案 | Keffect 可执行工作流、转换记录、不兼容项 | 后续规划 |
| 跑批验证能力 | 工作流、测试素材、验证要求 | 结果视频、执行记录、质量检查和失败报告 | 后续规划 |

当前目录 `skills/effect-generation-workflow/` 实际承担“链路设计能力”。从宏观职责看，`effect-chain-designer` 是更清晰的名称；为避免与正在进行的并行开发冲突，当前不立即重命名目录。正式重命名应在相关任务收口后统一进行，并同步修改引用、UI 配置和测试。

### 2.4 为什么当前不强绑定特定框架

当前主流程和模块依赖相对明确，可以先使用轻量的领域 Skill、结构化状态和顺序编排实现。设计上可以参考成熟框架的状态机、检查点、结构化输出和工具适配思想，但不为了形式完整提前引入复杂框架。

当出现以下真实需求时，再评估 LangGraph、Temporal 或其他编排方案：

- 大量动态分支、循环和人工审批；
- 多实例并发与分布式一致性；
- 长时间异步任务需要可靠队列和跨进程恢复；
- 自研重试、检查点和追踪成本明显升高。

## 3. 当前七步 Skill 的定位

当前七步流程属于完整 Agent 的“链路设计能力”，不是完整 Agent 的全部。

| Step | 职责 | 不负责 |
|---|---|---|
| Step 1 客观理解 | 记录视频中可观察的事实、主体、场景和时间线 | 卖点判断、链路选择 |
| Step 2 卖点判断 | 判断主次卖点、复刻目标和控制要求 | 把内容卖点固定绑定到某条执行链路 |
| Step 3 案例召回与链路选择 | 执行任务级案例主召回并选择链路类型 | 设计具体节点、模型参数和最终 Prompt |
| Step 4 链路设计 | 分开规划运行时输入槽位、固定素材、节点输出、模型和依赖 | 检查未来终端用户照片、准备真实素材、编写最终 Prompt |
| Step 5 素材准备 | 只取得、标准化并验证本次设计任务的固定素材 | 处理运行时输入槽位、执行生成节点、生成最终结果视频 |
| Step 6 Prompt 生成 | 基于运行时输入槽位、已就绪固定素材、上游节点输出和案例快照生成节点 Prompt | 重选链路、重做节点设计、重复主召回 |
| Step 7 方案验证与交付 | 检查方案完整性、一致性和引用有效性，交付生产方案 | 执行跑批或判断结果视频质量 |

链路类型按最终视频生成模型单次调用时实际接收的媒体入参判断：

- `single_image`：最终视频模型接收一张图；上游进行过多少次生图不改变分类。
- `reference_video`：最终视频模型接收参考视频，通常还会接收主体图。
- `multi_image`：最终视频模型需要至少两张图片表达不同精确状态。

内容卖点和执行链路必须分开分析。Step 3 应结合 Step 1 的视频客观理解、Step 2 的卖点与复刻目标、案例证据和模型控制需求做出判断，但不要求在证据不足时生硬硬判。

参考视频链路允许两种主体图片结构：运行时用户图直接与参考视频进入最终节点，或先由生图节点建立已确认的目标视觉状态，再将 `subject_image` 与参考视频进入最终节点。两者都属于 `reference_video`。Step 4 只在视频开始前确实必须建立造型、服装、道具、姿态、景别、身体可见范围或场景关系时增加前置生图；源视频主体外观本身不是充分理由。

## 4. 技术组件边界

| 组件 | 负责 | 不负责 |
|---|---|---|
| Skill / Prompt | 领域流程、判断标准、所需字段、结构化输出规范 | 通用任务持久化、文件锁、服务部署 |
| WorkflowEngine | 决定执行哪个模块和 Step、检查依赖与业务守卫、按链路路由执行器、推进状态 | 具体领域推理 |
| TaskStore | 任务创建、读取、校验、状态更新、原子保存和恢复 | 决定链路类型或编写 Prompt |
| RAG | 案例结构化、检索、排序、快照和证据返回 | 控制主流程状态、替代 Step 3 的最终判断 |
| 模型适配器 | 统一模型请求、响应、超时和错误表达 | 决定业务流程或直接写任务状态 |
| 素材管理 | 素材取得、生成、标准化、验证、存储和稳定引用 | 重选链路、改变节点设计 |
| 顶层 Agent 状态 | 记录整个任务处于哪个能力阶段及其产物 | 保存每个 Skill 的全部推理细节 |
| 工作台 / API | 提交任务、展示进度、补充输入、查看交付 | 承担领域判断和状态文件内部维护 |

真实或确定性 Step 的统一调用边界是：

```text
WorkflowEngine 构造 StepContext
  → StepExecutor 选择 Prompt 并调用模型或工具
  → Prompt 返回当前 Step 的业务 output
  → StepExecutor 包装 StepResult
  → TaskStore 校验并保存
```

`StepContext.resources` 注入 Prompt 路径、模型参考目录、案例快照读取器和后续适配器。这些是只读运行依赖，不进入 `task-result.json`。当前模型目录来自历史标注案例，只为 Step 4 提供设计师可读的候选模型、观察用途和可信度，不代表官方能力或接口可用性已经验证。执行器上下文不暴露 `task_result_path`，避免把状态文件写入能力扩散到 Prompt 或业务执行器。

当前已增加 provider-neutral 的结构化模型执行接口：它负责读取当前 Prompt、组合已校验输入与媒体引用、调用模型客户端并接收 JSON，再包装为 `StepResult`。它不是模型，也不包含具体供应商 API；当未来接入公司模型时，Step 2、4、6 可以复用同一执行器，只替换模型客户端。Step 1 在此基础上增加视频预处理和媒体输入。

当前仓库已经实现 WorkflowEngine、文件版 TaskStore 和三种运行路径：`--mock` 用于纯状态测试；`--manual` 使用 Codex 文件交换处理 Step 1/2/3B/4/6，Step 3A 仍执行本地 Embedding 真实召回；`--deepseek` 用于“Step 1 Codex 人工多模态 + Step 2/3B/4/6 真实 DeepSeek + Step 3A 本地 Embedding”混合运行。Step 5 已接入确定性 FFmpeg 素材处理，Step 7 已接入方案校验与 `production-plan.md` 交付。CLI 自动读取项目根目录 `.env.local`，但已有系统环境变量具有更高优先级；密钥不得写入任务状态、请求产物或 Git。

Agent 现已提供原生批次调度：`batch create/show/run/resume` 管理一组任务，使用有界线程池并行推进，但每条任务仍由自己的 WorkflowEngine 状态机、任务目录和文件锁隔离。批次状态只汇总任务状态，不复制七步业务结果；单任务异常会被记录，不取消其他任务。该能力是 Agent 运行时的一部分，与 Codex 多 Agent 调度无关。当前是单机并发，不等同于后续数据库队列或多机分布式调度。

### 4.1 Codex 文件交换调试模式

```text
WorkflowEngine 运行当前 Step
  → 无人工结果时写 manual/step-<n>/request.json
  → 任务以 needs_input 暂停
  → Codex 只提交当前 Step 业务 JSON
  → TaskStore 预校验候选输出
  → 写入匹配 request_id 的 response.json
  → resume 重新执行并由 TaskStore 正式提交
```

- `request.json` 包含 Prompt、Schema 版本、目标字段、结构化输入和媒体路径；Step 4、6 还包含模型能力与 Step 3 选中案例内容。
- `submit` 不能指定其他 Step，也不能直接修改任务状态；不合法 JSON 或不符合当前任务 Schema 的结果不会覆盖原状态。
- Step 1 首次请求前执行一次全局抽帧；恢复时复用相同预处理产物。`reused` 是运行证据，不改变同一人工请求的身份。
- 此模式是当前没有真实模型 API 时的调试入口，不是最终部署接口。以后接入模型服务时保留 `StructuredModelClient` 边界并替换客户端。

## 5. 任务状态设计

### 5.1 当前 `task-result.json`

当前阶段每个链路设计任务维护：

```text
outputs/<task-id>/task-result.json
```

它是当前七步运行的状态快照，记录：

- 任务标识、版本、时间和整体状态；
- 当前 Step；
- 源视频和输入引用；
- Step 1–7 的状态、输入引用、输出和错误；
- 案例快照、素材和交付物的路径；
- 未解决问题和风险。

Schema 文件 `schemas/task-result.schema.json` 只定义结构，不能写入实际任务数据。

### 5.2 Step 如何读取输入

每个 Step 的 Prompt 应明确列出所需的精确字段路径和字段用途。未来由 WorkflowEngine 从任务状态、案例快照和素材记录中构造 Step 输入，而不是让模型自行猜测应该读取哪个文件或字段。

Prompt 接收结构化上下文并返回结构化结果，不直接：

- 打开或覆盖 `task-result.json`；
- 决定状态保存位置；
- 修改其他 Step 的输出；
- 修改 Schema；
- 绕过 WorkflowEngine 或 TaskStore 推进任务状态。

### 5.3 状态由谁写入

当前实现中，只有 TaskStore 可以提交状态修改：

```text
读取当前状态
  → 校验版本和前置依赖
  → 构造当前 Step 输入
  → 执行 Prompt / 模型 / 工具
  → 校验当前 Step 输出
  → 只更新允许的字段
  → 校验完整任务
  → 原子保存
```

TaskStore 使用跨平台任务锁和同目录临时文件原子替换；写入前校验完整任务，校验或保存失败时保留上一份有效状态。StepExecutor 只能返回结构化结果，不能直接持久化状态。

### 5.4 状态语义

当前任务状态：

- `initialized`：任务已创建，尚未执行；
- `running`：正在执行；
- `needs_input`：缺少设计师本次必须提供的选择/固定信息或素材，或等待当前人工模型结果，补充后可以继续；不用于等待未来终端用户图；
- `blocked`：等待外部模型、服务或资源恢复；
- `completed`：当前任务目标已完成；
- `failed`：出现当前协议下不可恢复的任务错误。

Step 状态：

- `pending`
- `running`
- `completed`
- `needs_input`
- `blocked`
- `failed`

恢复任务时不得丢弃已经完成的 Step。进程中断时遗留的 `running` 不能被当作完成，应重新检查输入、产物和可重试性后继续当前 Step。

当前业务守卫已经覆盖：

- Step 4 根据 Step 3 的 `selected_chain` 路由到单图或参考视频执行器；
- `multi_image` 进入双图有序状态的 Step 4–6 执行器；`unsupported` 仍以 `chain_not_executable` 阻塞；
- Step 6 只有在 Step 5 的 `ready_for_prompting` 为 `true` 时执行。

当前恢复能力只重试当前 Step，不支持自动回退。Step 5 发现素材事实与 Step 4 设计矛盾时，以 `blocked` 和 `design_revision_required` 保存证据及建议复查步骤；不自动清除已完成结果。用户补充输入的正式持久化接口和受控回退能力留待真实试跑后设计。

### 5.6 视频理解与候选帧生命周期

```text
原视频
  → Step 1 执行器调用一次 extract-video.py
  → 元数据 + 原始分辨率候选帧 + frames.json + 时间线总览
  → VLM 同时理解完整视频并参考候选帧
  → VLM 筛选、标注关键帧及下游价值
  → Step 2 独立判断卖点
  → 离线评测器再与人工试跑记录比较
```

- FFmpeg 预处理不理解内容、不判断卖点和素材用途；相同视频及完整产物默认复用。
- 人工试跑结论不进入 Step 1/2 输入，避免提示答案；只能在两个 Step 完成后用于离线比较。
- Step 4 决定哪些关键帧或候选帧用于实际节点，并把稳定帧引用写入素材要求。
- Step 5 默认复用 Step 1 的原始分辨率文件，只做验证和已规划加工，不重新运行全局抽帧。
- 现有候选帧确实无法满足 Step 4 用途时，可以针对明确时间点或片段异常提取，但不得覆盖 Step 1 manifest，且必须记录原因和来源。

### 5.7 Step 5 素材操作约定

Step 4 在 `base_materials[].requirements` 中按以下结构提出固定素材计划，Step 5 只执行该计划，不处理 `runtime_inputs`，不自行增加生产节点：

- `source`：`user_material`、`step1_frame`、`source_video`、明确文件路径或人工生成素材；
- `operation`：`direct`、`crop`、`transform`、`image_to_image`、`generate`；生成操作必须通过自动素材生成接口执行；
- `target`：媒体类型、格式、宽高、适配方式，以及视频需要的可选时长；
- 操作参数：按需提供 `crop`、`clip` 或 `timestamp_seconds`。

确定性操作通过 FFmpeg 在 `materials/` 生成临时文件并原子替换，源文件只读。符合规格的既有产物会被幂等复用。`image_to_image` 当前不接生图 API，而是生成 `manual/image-generation/<material-id>/request.json` 并以 `needs_input` 暂停；Codex 把图片和内容核验 `evidence.json` 放入指定路径后，恢复 Step 5 重新执行技术规格与凭据检查。必需素材不得静默跳过或降级。

### 5.8 离线人工基线评测

Step 1、2 完成后可以单独导出它们与指定人工试跑文档的对比请求。对比结果保存在任务 `evaluations/`，不进入任何生产 Step 输入、不改写 Step 1/2 输出，也不推进工作流状态。

链路盲测使用无链路标签的视频文件名、中性任务 ID 和中性输出目录。人工答案不进入模型请求，必须在 Step 3 结果保存后由评测层对照。包含 `单图驱动`、`参考视频`、`single` 或 `reference` 的历史试跑只能用于工程闭环审计，不能计入正式准确率。

### 5.9 后续状态分层

当第二、第三个能力模块开始实现时，应区分：

- **AgentTask**：记录整个视频或批次任务、当前能力阶段、各模块运行引用、整体产物和全局错误；
- **SkillRun**：记录某个能力模块的一次运行及其内部步骤。

当前 `task-result.json` 更接近链路设计模块的 SkillRun。顶层 AgentTask 的具体字段和物理存储格式尚未确定，不在当前 Schema 中提前猜测或冻结。

## 6. Schema 维护原则

### 6.1 当前事实源

`schemas/task-result.schema.json` 是当前唯一的机器校验事实源，但它是持续演进的工作草案，不是已经冻结的最终协议。

Step 和 RAG 开发可以根据实际需要提出或实施字段调整。目标是让 Schema 随真实案例和运行需求收敛，而不是为了保持文件不变阻碍设计。

### 6.2 修改时的同步范围

字段新增或调整时，应结合影响范围同步检查：

- `schemas/task-result.schema.json`；
- 使用该字段的 Step Prompt；
- `SKILL.md` 中的路由或字段说明；
- fixture 和 Schema 测试；
- 案例快照或 RAG 输出；
- 已有任务的兼容性。

不要求每次探索都一次解决全部下游问题。暂时无法同步时，应在本文“待确定”或相关文件中明确记录缺口，避免把不一致误认为已确认设计。

### 6.3 版本规则

以下变化会破坏兼容性，需要升级 `schema_version` 并说明迁移方式：

- 删除已有字段；
- 改变字段语义；
- 改变字段类型；
- 将已有可选字段改为必填；
- 改变状态值的含义；
- 改变 Step 或模块职责导致旧数据被重新解释。

增加兼容的可选字段、补充描述或放宽不合理约束，可以在确认不影响已有数据后保留当前兼容版本。

`v0.2.0` 将 Step 1 从扁平观察字段调整为 `content_summary`、`narrative_structure`、`observations` 和 `key_frames`，并增加一次性视频预处理产物引用；Step 2 卖点证据增加 `evidence_frame_ids`。`v0.3.0` 将 Step 4 的运行时输入从固定素材中拆出为必填 `runtime_inputs`，并将 Step 5 收窄为只处理 `base_materials`。`v0.4.0` 引入 Prompt 分支，`v0.5.0` 收口固定素材和节点 Prompt，`v0.6.0` 增加跨 Step 约束来源，`v0.7.0` 增加 Step 6 防复制、语义复核和一次修正，`v0.8.0` 将外观策略移动到实际设计发生的 Step 4。`v0.9.0` 进一步将外观策略收敛为 `preserve_input`、`uniform_redesign`、`presentation_specific_redesign` 三种模式，避免一边声明保留输入、一边在 Prompt 中擅自指定造型。旧版任务不能只改版本号，需使用显式迁移命令或重跑相关步骤。

Step 4 的外观判断采用“模型提取事实、运行时执行公式、最多修正一次”的协议。事实包括是否明确要求保留原造型、是否适用成人 `female/male` 呈现、是否存在目标主体造型、该造型是否可选。首次事实一经提取即冻结，修正后不再让模型重新解释。成人主题人物造型使用人物呈现分支；婴幼儿、宠物和非人物造型采用统一重设计；明确保留原外观或纯身份替换采用保留输入。Step 6 还必须服从 Step 2 `adapt`：不得把应随运行时主体变化的年龄、物种和身体形态固定为源视频属性。

同一事实复核还判断首帧是否需要热点视觉锚点。复杂场景、构图、姿态、景别、道具或空间关系需要稳定复刻且存在可用 Step 1 关键帧时，运行时要求 Step 4 将该原分辨率帧作为 `base_materials` 固定输入，并让前置生图节点同时引用运行时身份图。Step 5 负责复制和验证关键帧，Step 6 明确“用户图负责身份、热点帧负责视觉状态”。这类前置多参考生图不改变最终视频链路分类。

### 6.4 Pydantic 迁移时机

当前继续直接维护 JSON Schema。满足以下条件后，再集中迁移为“Pydantic 模型是代码事实源、JSON Schema 由模型生成”：

- Step 1–3 的核心输出已经过至少一轮真实任务验证；
- case schema、案例快照和召回输出基本稳定；
- Step 4–6 的节点、素材和 Prompt 字段完成端到端试跑；
- WorkflowEngine 和 TaskStore 的最小接口已经明确。

迁移前不同时维护一份手写 Pydantic 字段和一份手写 JSON Schema，避免双重事实源。

## 7. 案例快照与任务记录

`task-result.json` 和 `case-snapshot.json` 服务于不同目的：

| 文件 | 记录内容 | 生命周期 |
|---|---|---|
| `task-result.json` | 任务状态、Step 输出、选中案例 ID、快照引用和使用证据 | 随任务推进更新 |
| `case-snapshot.json` | Step 3 本次召回得到的案例内容、检索上下文和版本信息 | 主召回完成后保持稳定；补充召回应显式记录 |

“根据引用读取”表示：先从任务状态取得快照路径和 `case_ids`，再到案例快照中读取对应案例。任务状态不复制整份案例内容，以免案例快照和任务记录形成两份不同版本。

静态 Prompt 示例只解释某个 Step 可能如何正确输出，不属于任务案例快照，也不能作为模型能力证据。

## 13. 当前链路设计 MVP 验收标准

- Step 1–7 均有明确输入、输出和失败状态；
- Step 3 执行一次主召回并保存任务级案例快照；
- Step 4 负责节点、模型和素材规划，不提前写最终 Prompt；
- Step 4 的 `runtime_inputs`、`base_materials` 和 `nodes[].outputs` 角色清晰且 ID 可唯一解析；
- Step 5 只取得或确认方案需要的固定素材，不因运行时用户图不存在而暂停；
- Step 6 可引用运行时槽位、已就绪固定素材和上游节点输出；
- Step 7 能区分验证三类引用，并按 `node_id` 把 Prompt 内嵌到设计师可读节点方案；
- 单图和参考视频需求能够选择正确链路并输出可执行生产方案；
- 双图有序状态需求进入多图链路；超出该边界的需求返回明确的不支持结果，不被错误归入单图；
- 事实、推断、案例证据、风险和缺失项可追溯；
- Schema、Prompt、案例快照和任务记录之间的引用一致。
